# TBMdataAn

TBM运行数据审计与初始预测基线。项目检查多设备导出数据的字段完整性、时间连续性和跨设备重复，并建立严格按时间划分的多步预测比较。

## 本轮结果

- 审计1,531个原始CSV，共7,628,284行，另审计Excel汇总表1,035,283行。
- 发现不同TBM编号下的时间戳和四个核心信号存在完全相同记录；在当前基线中隔离相关源文件双方，共210个文件。
- 清理后，TBM5、TBM6、TBM8、TBM9、TBM10满足本轮训练、验证和测试条件。
- 比较持久性、Ridge增量回归和梯度提升树，预测30、60、120秒后的推力、扭矩和推进速度。
- 当前回归模型尚未稳定超过持久性基线；设备单位及部分数据来源仍待核实。

## 最小验证方案（已在真实数据上运行）

- 检验固定基线为何难以超过持久性：时间标签核查、训练样本量、简单预测基线、按未来状态分层的误差归因、公平的同机与留一机器比较，以及探索性的毛刺污染实验。
- 主要结果：“打不过持久性”被平方损失与MAE评价错位、训练期v毛刺这两个协议问题夸大；改用MAE损失并用全部训练窗口后，TBM8、TBM10、TBM9在27个（时域×目标×机器）组合中的26个显著优于持久性（0.3%到20.1%），TBM5、TBM6没有一个优于。F目标上持久性30%到79%的误差来自占1%到15%窗口的停机事件，测试过的模型都不能可靠预测它们。训练量匹配后，跨机器训练没有一致的好处。
- 结果、判定规则和局限见[最小验证方案实验结果](analysis/outputs/最小验证方案实验结果.md)；方案与预设规则见[最小验证方案与初步诊断](analysis/outputs/最小验证方案与初步诊断.md)。

## P0 可信机器与数据源清单（已在真实数据上运行）

- 检验跨机器重合、来源和单位：逐行哈希、里程计数器接续、物理量之间的固定关系，输出文件级、行级和数据流级清单。
- 主要结果：TBM6-2024和TBM2-2024两个目录（135个文件）是TBM5-2024的逐行副本，TBM5-2024是真实数据；TBM9有两个文件混入TBM10的数据；TBM9的转速列在119个文件里装的不是转速（占其活动行的42.4%）；TBM10-2023有4个文件的推进速度无效；其余单位关系内部自洽。1,531个文件中1,271个可使用（98个带标记），119个需修复，其余排除或截断。
- 结果、规则、对已有结果的影响和需要你确认的问题见[P0可信机器与数据源清单](analysis/outputs/P0可信机器与数据源清单.md)；数据在[analysis/outputs/p0](analysis/outputs/p0/)。

## 标准时序数据v1（P1，已在真实数据上运行）

- 统一字段、时间戳和质量标记：39个标准字段、行级质量标记（`q_*`）、默认的值有效筛选`valid_core`，输入是P0的可信清单。
- 结果：9台机器、14条数据流、6,608,202行（原始7,628,284行中排除999,007行P0判定的副本和外来行，丢弃21,075个整行完全相同的重复行）；TBM9的转速列按默认处理用v/p还原（原值保留）；可用于预测的机器TBM5、TBM6、TBM8、TBM9、TBM10共989,726个有效活动行（占全部活动行的99.4%）。81项检查通过。
- 数据卡见[标准时序数据v1数据卡](analysis/outputs/标准时序数据v1数据卡.md)；字典、账目和校验结果在[analysis/outputs/standard_v1](analysis/outputs/standard_v1/)（parquet数据文件由脚本重建，不纳入Git）。

## 连续掘进段与阶段划分（P2，已在真实数据上运行）

- 在标准时序数据v1上，按机器自己的掘进状态建立连续掘进段（读数间隔不超过60秒，状态为开而推力连续为0达120秒的行切出段外），并把≥5分钟的长段划分为上升、稳定、下降三个阶段；每一行都有段号、阶段码和运行状态，没有删行或插值。范围是TBM5、TBM6、TBM8、TBM9、TBM10。
- 结果：15,169个段、3,945小时，其中长段9,193个占段时间的96.7%；9,008个长段（98.0%）找到稳定阶段。机器的掘进状态与信号基本一致（有活动的行几乎全在状态为开的行里，反过来K1型的状态为开约有8%到9%的行并不活动）。阶段边界对阈值敏感，应当当作±1到3分钟的约定。读数缺口让长段里8.5%至少一侧边缘被截断，表里标为`censored`。
- 人工抽样验证包（98页图、答题表、评分脚本）已备好，**需要现场工程师填写**；我自己看了这98页做了自查，但规则是边看边改的，不是独立验证。72项检查通过，合成数据自检29项通过，重建逐字节一致。
- 报告见[P2分段与阶段划分报告](analysis/outputs/P2分段与阶段划分报告.md)；段表、汇总、敏感性和验证包在[analysis/outputs/segments_v1](analysis/outputs/segments_v1/)（逐行标签的parquet文件由脚本重建，不纳入Git）。

## 复现

使用Python 3.11，依赖版本见[requirements.txt](analysis/requirements.txt)。先按[原始数据说明](data/raw/README.md)下载Git LFS压缩包并运行`python analysis/restore_raw_data.py`，将原始数据还原至`TBMData/TBMData/`；再按[分析说明](analysis/README.md)依次运行审计、重复核查、基线、报告、验证和P0、P1、P2脚本。

仓库包含代码、审计统计、模型指标、报告、图表，以及通过Git LFS保存的全部原始输入无损压缩包和SHA-256清单。解压后的原始目录、重复压缩备份、本地Python环境及生成的Parquet数据集、模型二进制、逐窗口预测缓存不纳入Git；这些派生文件可通过脚本重建。

原始数据的设备编号与真实来源需进一步核对。当前指标使用未经单位转换的导出数值，不应据此推断地质状态、故障风险或最优控制策略。
