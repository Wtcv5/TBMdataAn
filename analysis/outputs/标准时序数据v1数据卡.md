# 标准时序数据 v1 数据卡

路线图第二步：统一字段、时间戳和质量标记。输入是[P0可信机器与数据源清单](P0可信机器与数据源清单.md)，处理按P0报告第七节写明的默认处理进行（你确认“按默认处理继续”）。数据是每台机器一个parquet文件，在`analysis/outputs/standard_v1/`；parquet文件由脚本重建（约80秒，不纳入Git），清单、字典和校验结果纳入Git。

## 结论先行

1. **v1包含9台机器、14条数据流、6,608,202行**，来自1,395个原始文件。原始7,628,284行中，999,007行因P0排除（135个副本文件加TBM9的4,964个外来行），21,075行是整行完全相同的重复（只出现在TBM2-2023和TBM3-2024-part2），其余全部保留，没有插值、平滑或丢弃异常值。每个文件的账目都对得上（原始＝P0排除＋无效时间＋完全重复＋保留）。
2. **字段统一为39列**：5个核心信号（F、T、n、v、p）、机器自己的4个状态码、3个位置计数器、3个驱动电机汇总量、时间、来源标识、12个质量标记和两个便利列（`active`、`valid_core`）。同一个标准字段在不同机型里对应的原始列见[column_map.csv](standard_v1/column_map.csv)，字典和单位状态见[field_dictionary.csv](standard_v1/field_dictionary.csv)。
3. **转速n按默认处理修复**：TBM9有113,754个活动行的`刀盘实际转速`装的是电机频率，已用v/p还原，原值保留在`n_raw`，来源记在`n_source`。另一条独立路径（电机频率×0.061）在这113,870行上与v/p还原相差中位数0.0%（5%到95%分位−0.05%到+0.06%），两条路径互相印证。做“n缺失”敏感性时取`n.where(n_source=='exported')`。
4. **质量标记只标记，不删除**。`valid_core`是默认的值有效筛选（无负值、核心信号齐全、没有超限的v/T/F、不在v无效文件里、没有冲突时间戳）：全部活动行995,671行中989,726行（99.4%）通过。可用于预测的机器及其有效活动行数是TBM5 233,640、TBM6 166,934、TBM8 127,630、TBM9 264,995、TBM10 191,938；TBM1到TBM4缺扭矩或推力，不能用。
5. **验证**：81项检查通过（清单与manifest一致、行账目、排序和时间差、标记可由存储的列重新算出、转速修复的一致性、60个文件8,994个值与原始CSV重读一致、全部6,608,202行与审计的缓存逐值一致）；合成数据自检18项通过，期间植入的问题全部落到对应的标记上。

## 四、时间戳

- 全部1,395个文件的时间都能解析，**没有无效时间**。时间是文件里的本地时间，时区没有确认。
- 每台机器的所有数据流合并后按（时间，文件，行号）排序。文件内时间倒退只有6行（TBM3-2023的3行、TBM4-2024的3行），标记`q_time_backward`；排序后不再倒退。
- 同一台机器上时间戳和全部取值都相同的行只保留第一行（21,075行，TBM2-2023的20,148行和TBM3-2024-part2的927行）。时间戳相同而取值不同的行全部保留并标记`q_time_conflict`：TBM2-2023有5,916行，TBM3-2024-part2有862行，其余机器没有。这些行出现在时间戳只精确到分钟的文件里（`q_time_coarse`：7,768行和1,868行），一分钟里有多行真实采样。

## 五、质量标记

标记都是布尔列，行级，可叠加。阈值在`p1_standardize.py`开头，与P0用同一套常数。

| 标记 | 含义 | 全部行数 |
| --- | --- | --- |
| `q_time_backward` | 时间早于文件里的上一行 | 6 |
| `q_time_coarse` | 文件的时间戳只精确到分钟（P0） | 9,636 |
| `q_time_conflict` | 同一台机器另有行时间戳相同、取值不同 | 6,778 |
| `q_neg` | F、T、n、v、p中有负值 | 3,196 |
| `q_core_missing` | F、T、n、v中有空值（含导出里没有这一列） | 1,047,046 |
| `q_n_invalid` | 导出的n不是转速：超过12 rpm，或与电机转速一样大（比值大于0.5） | 162,792 |
| `q_v_high` | v超过250 mm/min | 6,103 |
| `q_T_high` | T超过12,000 | 4,555 |
| `q_F_high` | F超过60,000 | 0 |
| `q_pnv_off` | 贯入度×转速÷推进速度在0.5到2之外（v、p、n都够大时才判） | 532 |
| `q_v_invalid_file` | P0判定整个文件的v和p不可用 | 16,542 |
| `q_counter_glitch` | 位置计数器偏离本文件开头的水平超过5（米或环），依据P0找出的跳变 | 9,323 |

`valid_core`＝不满足`q_neg`、`q_core_missing`、`q_v_high`、`q_T_high`、`q_F_high`、`q_v_invalid_file`、`q_time_conflict`中的任何一个。`q_core_missing`的大数来自TBM1到TBM4（缺扭矩或推力，共1,019,869行）；`valid_core`为真的5,534,111行里几乎都来自其余五台机器，这五台机器自己的通过率在96%到100%。各条数据流的明细在[flag_summary.csv](standard_v1/flag_summary.csv)。

关于具体标记的几点说明：

- **`q_v_high`并不都是传感器毛刺。** TBM9的1,623行和TBM10不在v无效文件里的363行全部发生在活动行（正在掘进），是毛刺；TBM5的1,067个超限行里，421个在掘进中（孤立的单行毛刺），530个处在机器自己的“换步”状态（油缸快速运动，F＝0，v是油缸速度），其余是其他非掘进状态。把它们都当作“不是推进速度”是合理的默认，但做误差归因时应区分。
- **`q_T_high`的12,000是保守的上限。** 各机器的扭矩主体在7,000以下，8,000到12,000之间有零星读数（TBM5的活动行中约230个），未标记。T超限行主要出现在停机时（TBM5的3,873个中活动行只有75个）。
- **`q_counter_glitch`只标记，不改值。** 这些跳变在P0里已逐一列出（[counter_events.csv](p0/counter_events.csv)）：多数发生在停机时，按计数器自身的暂时错位处理。
- **`q_n_invalid`的构成**（见第六节）：TBM9的140,886行、TBM10的21,891行（停机时的卡死读数39.7）、其余机器合计15行。

## 六、转速n的处理

规则（逐行）：导出的`n`超过12 rpm，或`n`大于等于0.5且与驱动电机转速之比超过0.5（正常时该比值为0.06或0.003），就不是转速，记`q_n_invalid`。然后：

1. 该行`v`和`p`都大于0：`n`＝v/p（`repaired_v_over_p`）；
2. 否则，机器有电机转速常数且电机在转：`n`＝常数×电机转速中位数（`repaired_drive_speed`），常数取自该机器通过P0检验的文件（TBM9为0.0610）；结果超过12 rpm则放弃；
3. 否则`n`为空（`unrecoverable`）。

| 机器 | 导出值（`exported`） | v/p还原 | 电机转速还原 | 无法还原 |
| --- | --- | --- | --- | --- |
| TBM9 | 1,090,911 | 113,870（其中活动行113,752） | 21,588（几乎都在停机，n约0到5.8） | 5,428（`n_raw`为12.3到91.9，中位数39.7） |
| TBM10 | 982,703 | 0 | 156 | 21,735（`n_raw`几乎恒为39.7，停机时的卡死读数） |
| TBM5 | 1,872,233 | 0 | 2 | 8 |
| TBM6 | 1,170,205 | 0 | 0 | 4 |
| 其余 | 全部 | | | TBM3有1行，另有3行n本身为空（`missing`） |

- 两条独立路径的一致性：在TBM9的113,870个v/p还原行上，用电机转速常数算出的n与v/p的相对差中位数为0.0%，5%到95%分位为−0.05%到+0.06%。因此第1、2条规则给出同一个数。
- 无法还原的行几乎都在停机（TBM9的5,428行里F大于0的35行，TBM10的21,735行里15行；TBM10这些行的T中位数只有70）。
- 与旧流程的差别：旧流程把TBM10停机时n＝39.7的卡死读数当作有效的有限值，若落在历史窗口里就会成为输入特征；v1里这些行的`n`为空，`valid_core`为假。这对基线的实际影响留到P5核对。

## 七、验证

[p1_verify.py](../p1_verify.py)只读，81项全部通过，结果在[verification.json](standard_v1/verification.json)：

- manifest：9个文件的行数和逐列校验和与记录一致（parquet文件的字节哈希也记录在内，但不同的pyarrow版本可能写出不同的字节，所以只作提示）；P0输入文件的哈希与构建时一致。
- 账目：每个文件原始＝P0排除＋无效时间＋完全重复＋保留；保留行数等于数据里该文件的行数；没有P0排除的文件出现；截断文件只保留截断点之前的行。
- 时间：每台机器按（时间，文件，行）排序；`dt_prev_s`等于时间差；`q_time_conflict`恰为重复的时间戳；没有完全相同的行。
- 标记：值类标记、`active`、`valid_core`都能由存储的列重新算出；`n_source`与数值一致（v/p还原行满足n＝v/p，导出的n不超过12 rpm，无法还原的n为空）。
- 原始数据：随机60个文件、每个25行，用另一段读取代码重读原始CSV，时间、F、T、v、p、导出的n和掘进状态共8,994个值全部一致。
- 机器之间：任意两台机器的数据里没有相同的活动读数（时间、F、T、n、v完全一致的行为0；原始导出里有4对机器共享这样的行）。
- 与审计的缓存对比：6,608,202行的时间、F、T、v、p和导出的n与`canonical`缓存逐值一致，说明标准化没有改动任何读入的值；变化只来自`n`的修复、排除的行和丢掉的重复行。

[smoke_test_p1.py](../smoke_test_p1.py)用合成的原始导出植入P0发现的各类问题，运行真实的审计、P0脚本和标准化，检查18项：副本消失、外来行截断、整文件外来数据消失、整文件错位的n被还原且保留`n_raw`、交替行的错位只落在被植入的行、坏v的文件整体标记、毛刺行恰为被植入的行、计数器偏移恰为1000到1299行、分钟时间戳被标记、TBM8的递减里程不误报，以及第二次构建的校验和相同。

## 八、使用与限制

读取与默认筛选：

```python
import pandas as pd
d = pd.read_parquet('analysis/outputs/standard_v1/TBM9.parquet')
use = d[d.valid_core]                                    # 值有效的行（全运行视图的起点）
act = d[d.valid_core & d.active]                         # 其中正在掘进的行
exported_only = d.n.where(d.n_source == 'exported')      # “n缺失”敏感性版本
```

限制，下一步要注意：

1. `valid_core`是默认筛选，不是唯一答案。v毛刺是标记而不是删除，是否进训练集由P3/P5决定；实验E已经表明这对v的结果影响很大。
2. n的还原是估计。两条独立路径一致，但“TBM9的n列装的是电机频率”本身来自内部自洽，口径要你确认（P0的Q3）。
3. `state_boring`有缺口：TBM5-2023只有25.6%的行有值，P2要用`state_thrust`补前期，或者从信号推断掘进状态。机器自己的状态码含义（`state_cutter`、`state_thrust`的取值）没有字典，只知道取值与活动行的关系（例如`刀盘工作状态`为6时90%以上的行是活动行）。
4. 位置计数器不能直接当作可比较的位置：`cutter_mileage`在TBM5、TBM6带约±735,000的偏移，且两台符号相反；`ring`在TBM9有大段缺失。
5. TBM5-2023和TBM6-2023在文件内部有大量超过60秒的缺口，TBM8的采样间隔不规则（恰为10秒的只有43%）。
6. 时间的时区没有确认。
7. TBM9受影响期间的非核心列（P0发现332列中61列相差10倍以上）**没有进入v1**；v1只取核心列、状态码、计数器和电机汇总量，并用P0已核对过的关系检验。
8. P0清单里的默认处理（尤其Q1的归属）如有变化，v1需要重建。
